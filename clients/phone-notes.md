# Phone setup

How the phone was configured with the official WireGuard app, generating the key pair
**on the device** so no private key ever travels.

## Why not a QR code

The usual shortcut is generating the whole config (private key included) on the server
and importing it as a QR code. That is convenient, but it means the client's private key
is created outside the device and travels to it.

The approach used here is the opposite: the app generates its own key pair, and only the
**public** key is handed over to be registered on the VPS. Slightly more manual, but the
private key never leaves the phone.

## 1. Create the tunnel

1. Install the official **WireGuard** app.
2. Tap **+** → **Create from scratch** (not "import").
3. The app generates a key pair automatically. Copy the **public key** it shows.

## 2. Register the peer on the VPS

Append to the VPS `/etc/wireguard/wg0.conf`:
```ini
[Peer]
# Phone
PublicKey = <PHONE_PUBLIC_KEY>
AllowedIPs = 10.10.0.11/32
```

Apply it live without disturbing existing tunnels:
```bash
sudo wg set wg0 peer <PHONE_PUBLIC_KEY> allowed-ips 10.10.0.11/32
sudo wg show
```

Only the phone's own VPN address is listed: a phone is an endpoint, not a gateway, so
nothing is routed *through* it.

## 3. Fill in the tunnel — SPLIT profile

Home LAN access only; regular browsing keeps using mobile data.

**Interface**

| Field | Value |
|---|---|
| Name | `Home-SPLIT` |
| Private key | (generated by the app — leave it) |
| Addresses | `10.10.0.11/32` |
| DNS servers | leave empty |

**Peer**

| Field | Value |
|---|---|
| Public key | `<VPS_PUBLIC_KEY>` |
| Endpoint | `<VPS_PUBLIC_IP>:51820` |
| Allowed IPs | `10.10.0.0/24, <HOME_LAN_SUBNET>` |
| Persistent keepalive | `25` |

## 4. Second tunnel — FULL profile

All traffic exits through the VPS. To switch profiles with a single tap while keeping
**one identity**, the second tunnel reuses the same private key, so the VPS needs no
extra peer.

1. Open the SPLIT tunnel, copy its **private key**.
2. Create a new tunnel from scratch.
3. Replace the auto-generated private key with the copied one.
   The public key shown must become identical to `<PHONE_PUBLIC_KEY>` — that is the
   check that the identity was reused correctly. If it differs, the paste did not take.
4. Fill in the rest:

**Interface**

| Field | Value |
|---|---|
| Name | `Home-FULL` |
| Private key | same as the SPLIT tunnel |
| Addresses | `10.10.0.11/32` |
| DNS servers | `10.10.0.2` |

**Peer**

| Field | Value |
|---|---|
| Public key | `<VPS_PUBLIC_KEY>` |
| Endpoint | `<VPS_PUBLIC_IP>:51820` |
| Allowed IPs | `0.0.0.0/0` |
| Persistent keepalive | `25` |

### Why DNS only in the FULL profile

- **SPLIT**: normal traffic still uses mobile data with the carrier's resolver, so
  nothing needs changing.
- **FULL**: everything goes through the tunnel, DNS included. Without an explicit
  resolver, queries could leak or stop resolving.

`10.10.0.2` is the Pi's address inside the VPN, where Pi-hole listens. Queries therefore
travel through the tunnel and are filtered by Pi-hole and resolved by Unbound, which
means **ad blocking works on mobile data, away from home, with no app installed** — and
no public resolver sees the browsing history. Use a public resolver such as `1.1.1.1`
instead if Pi-hole is not deployed.

## 5. Testing

Activate the tunnel with **mobile data** (home Wi-Fi off) to genuinely simulate being
away. Testing the SPLIT profile from inside the home network is misleading, because the
phone already has a direct route to the home LAN.

Only one tunnel can be active at a time; enabling one disables the other.

Checks with SPLIT active:
- Open `http://<HOME_ROUTER_IP>` — the router page should load.
- Reach any other home device by its LAN address.

Checks with FULL active:
- Visit any "what is my IP" page — it must show the **VPS** public IP, not the
  carrier's.
- Browse a site with ads — they should be blocked by Pi-hole, over mobile data, with no
  app installed on the phone.

On the VPS, confirm the handshake:
```bash
sudo wg show
```
The phone peer should show a recent `latest handshake` and growing `transfer`. Its
`endpoint` will be the carrier's public address, which confirms the connection is
coming from outside the home network.

On the Pi, the Pi-hole admin interface (`http://<PI_LAN_IP>:8080/admin`) should list
queries arriving from the phone's VPN address, proving DNS is travelling through the
tunnel.
