# Clients — phone and laptop

Record of the WireGuard setup on the two remote clients, the phone (`10.10.0.101`) and the
laptop (`10.10.0.102`), and of adding them as peers on the VPS hub.

Each client has **two profiles that share one key and one address**:

- **SPLIT** (`casa-split`) — only VPN and home LAN traffic goes through the tunnel. It is
  used to reach home devices; internet traffic keeps going directly through the local
  network.
- **FULL** (`casa-full`) — all traffic goes through the tunnel and leaves to the internet
  from the VPS. It is used on untrusted networks (a café, a hotel).

| | SPLIT (`casa-split`) | FULL (`casa-full`) |
|---|---|---|
| `AllowedIPs` | `10.10.0.0/24, <HOME_LAN_SUBNET>` | `0.0.0.0/0, ::/0` |
| `DNS` | none (the local network's resolver) | `9.9.9.9`, reached through the tunnel |
| Home LAN reachable | yes | yes |
| Internet leaves from | the local network | the VPS (`<VPS_PUBLIC_IP>`) |
| IPv6 | untouched | captured and dropped (no leak) |

```
phone / laptop (10.10.0.101 / 10.10.0.102)
   │  encrypted, over UDP to <VPS_PUBLIC_IP>:51820
   ▼
VPS wg0 (10.10.0.1)  ── hub
   ├──► internet, NATed to <VPS_PUBLIC_IP> ............ FULL only
   └──► Pi wg0 (10.10.0.2) ──► home LAN (<HOME_LAN_SUBNET>)
```

> **Prerequisites**:
> - [VPS-WIREGUARD.md](VPS-WIREGUARD.md) done: the hub is up on `10.10.0.1/24`, with the
>   `FORWARD` and `MASQUERADE` hooks that FULL relies on.
> - [RASPBERRY-WIREGUARD.md](RASPBERRY-WIREGUARD.md) done: the Pi is connected and is the
>   gateway to `<HOME_LAN_SUBNET>`.

Placeholders (`<LAPTOP_PRIVATE_KEY>`, `<HOME_ROUTER_IP>`, ...) are defined in the
[README](../README.md#placeholders).

## Design points
1. **One key and one address per device.** Both profiles of a device use the same private
   key and the same `Address`, so the VPS sees exactly one peer per device and needs only
   one `[Peer]` section for it. The consequence: **never bring both profiles up at the
   same time**. They would fight over the same key and address; bring one down before
   bringing the other up.
2. **`::/0` in FULL captures IPv6.** The tunnel is IPv4-only (see the
   [design decision in VPS-WIREGUARD.md](VPS-WIREGUARD.md#design-decision-ipv4-only-tunnel)).
   With `::/0` in `AllowedIPs`, the client sends all its IPv6 traffic into the tunnel
   instead of out through the local network. The client has no IPv6 address in the
   tunnel, and the VPS only accepts packets from the peer's `10.10.0.10x` source, so that
   IPv6 traffic is dropped (and the VPS's IPv6 `FORWARD` policy is `DROP` as a second
   layer). Browsers and apps fall back to IPv4 within a moment, which
   does go through the tunnel, and nothing leaks through the local network.
3. **DNS for FULL is temporarily a public resolver.** `DNS = 9.9.9.9` (Quad9) is covered
   by `0.0.0.0/0`, so the queries travel inside the tunnel and leave from the VPS: the
   local network cannot see them. Once Pi-hole is installed on the Pi, it becomes
   `DNS = 10.10.0.2` (in a later document). SPLIT has no `DNS` line: it keeps using the
   local network's resolver, which is fine because SPLIT does not route the internet.
4. **No `PersistentKeepalive` on the clients.** The clients always start the connection,
   and nobody needs to reach them while they are idle. Without the keepalive the tunnel
   is silent when there is no traffic, which saves battery on the phone. (The Pi needs
   the keepalive because the VPS must be able to reach it at any moment; see
   [RASPBERRY-WIREGUARD.md §5.1](RASPBERRY-WIREGUARD.md#51-differences-from-the-hub).)
5. **No hooks on the clients.** They route nothing for anyone, so they need no `FORWARD`
   or `MASQUERADE` rules. For FULL, `wg-quick` handles the default route by itself: it
   marks the tunnel's own packets with `fwmark 51820` and adds policy routing rules, so
   everything goes into the tunnel except the encrypted packets to the endpoint, which
   keep using the normal route (otherwise the tunnel would try to carry itself).

## Part A — Laptop (Arch Linux)

### 1. Install WireGuard and a `resolvconf` provider
```
sudo pacman -S wireguard-tools
```
Installs the `wg` and `wg-quick` commands. The WireGuard module is already part of the
kernel.

```
ls -l /etc/resolv.conf
```
Shows how the laptop manages its DNS configuration, which decides the `resolvconf`
provider to use. `wg-quick` applies the `DNS =` line through the `resolvconf` command;
without one, `wg-quick up` fails for the FULL profile.

- A symlink to `/run/systemd/resolve/stub-resolv.conf` → systemd-resolved manages DNS; the
  provider is `systemd-resolvconf`.
- A regular file starting with `# Generated by resolvconf` → `openresolv` manages it;
  check with `pacman -Qo /usr/bin/resolvconf`, which prints the package that owns the
  command. (`openresolv` and `systemd-resolvconf` conflict; install only one.)

On this laptop it is a regular file starting with `# Generated by resolvconf`, so the
provider is `openresolv`.

### 2. Key pair
```
sudo install -d -m 700 /etc/wireguard
```
Creates `/etc/wireguard` (or resets its mode) owned by `root` with permissions `700`.

```
sudo sh -c 'cd /etc/wireguard && umask 077 && wg genkey | tee laptop_private | wg pubkey > laptop_public'
```
Generates the laptop key pair as `root`, with permissions `600`. It is the same command as
on the VPS, with different file names; every part is explained in
[VPS-WIREGUARD.md §3](VPS-WIREGUARD.md#3-key-pair).

```
sudo cat /etc/wireguard/laptop_public
```
Prints the laptop public key, `<LAPTOP_PUBLIC_KEY>`. It goes into the laptop peer on the
VPS (§7). The private key, `<LAPTOP_PRIVATE_KEY>`, never leaves the laptop.

### 3. The two profiles
`/etc/wireguard/casa-split.conf`:
```
[Interface]
Address = 10.10.0.102/24
PrivateKey = <LAPTOP_PRIVATE_KEY>

[Peer]
PublicKey = <VPS_PUBLIC_KEY>
Endpoint = <VPS_PUBLIC_IP>:51820
AllowedIPs = 10.10.0.0/24, <HOME_LAN_SUBNET>
```

`/etc/wireguard/casa-full.conf`:
```
[Interface]
Address = 10.10.0.102/24
PrivateKey = <LAPTOP_PRIVATE_KEY>
DNS = 9.9.9.9

[Peer]
PublicKey = <VPS_PUBLIC_KEY>
Endpoint = <VPS_PUBLIC_IP>:51820
AllowedIPs = 0.0.0.0/0, ::/0
```
`<LAPTOP_PRIVATE_KEY>` is the content of `/etc/wireguard/laptop_private`; `<VPS_PUBLIC_KEY>`
is the content of `/etc/wireguard/publickey` on the VPS.

```
sudo chmod 600 /etc/wireguard/casa-*.conf
```
Read and write for `root` only: both files contain the private key.

- **The file name is the interface name.** `wg-quick up casa-split` reads
  `/etc/wireguard/casa-split.conf` and creates an interface called `casa-split`.
- **Keep `Address` identical in both profiles**, `/24` included. A `/32` in one of them
  also works, because `AllowedIPs` adds the route to `10.10.0.0/24` anyway, but both
  profiles describe the same peer and should not differ.
- `AllowedIPs` and `DNS` are the only differences between the two profiles (see the
  table above).

## Part B — Phone (WireGuard app)
The phone profiles are built on the laptop and passed to the phone as a QR code shown in
the terminal, so the phone's private key never travels as a file, by chat or by email.

### 4. Keys and profiles, built on the laptop
```
sudo pacman -S qrencode
```
Installs `qrencode`, which turns a text file into a QR code.

```
mkdir -m 700 ~/wg-phone && cd ~/wg-phone
```
Creates a working directory readable only by the user, outside the repository, and enters
it.

```
umask 077
```
Files created from now on in this shell get permissions `600`.

```
wg genkey | tee phone_private | wg pubkey > phone_public
```
Generates the phone key pair: `phone_private` holds `<PHONE_PRIVATE_KEY>` and
`phone_public` holds `<PHONE_PUBLIC_KEY>`. No `sudo` is needed: the files stay in the
user's private directory and are deleted in §6.

Create `phone-split.conf` and `phone-full.conf` in `~/wg-phone` with an editor. They are
the laptop profiles from §3 with two changes:
```
Address = 10.10.0.101/24
PrivateKey = <PHONE_PRIVATE_KEY>
```
Everything else (`DNS`, the `[Peer]` section, `AllowedIPs`) is the same as in the
matching laptop profile.

### 5. Import by QR code
In the WireGuard app: **+** → **Scan from QR code** (Android; on iOS: **Add a tunnel** →
**Create from QR code**). Then, on the laptop:
```
qrencode -t ansiutf8 < phone-split.conf
```
Prints the SPLIT profile as a QR code in the terminal (`-t ansiutf8` draws it with text
characters). Scan it with the app and name the tunnel `casa-split`.

```
qrencode -t ansiutf8 < phone-full.conf
```
Same for the FULL profile; name it `casa-full`.

### 6. Keep only the public key
```
cat ~/wg-phone/phone_public
```
Prints `<PHONE_PUBLIC_KEY>`, needed for the phone peer on the VPS (§7). Copy it first: the
next commands delete the whole folder, public key included.

```
shred -u ~/wg-phone/*
rm -rf ~/wg-phone
```
`shred -u` overwrites and deletes every file in the folder: the phone's private key, both
profiles (which contain it) and the public key. `rm -rf` then removes the folder itself.
Editor swap/backup files in that folder are removed with it. The phone's private key must
live **only on the phone**: the app already has it.

> On SSDs and journaling/CoW filesystems `shred` cannot guarantee the data is
> overwritten. Also close the terminal (or clear its scrollback) after scanning, since the
> QR code encodes the private key.

> **Alternative**: generate the key inside the app (**+** → **Create from scratch** →
> **Generate**) and copy only the public key to the VPS. It is stricter: the private key
> never exists outside the phone.

## Part C — Peers on the VPS

### 7. Add the clients as peers on the VPS
These steps run **on the VPS**.

```
sudo nano /etc/wireguard/wg0.conf
```
Append at the end of the VPS configuration:
```
[Peer]
# Phone
PublicKey = <PHONE_PUBLIC_KEY>
AllowedIPs = 10.10.0.101/32

[Peer]
# Laptop
PublicKey = <LAPTOP_PUBLIC_KEY>
AllowedIPs = 10.10.0.102/32
```
- `PublicKey` — the client's public key: the VPS accepts only packets encrypted with the
  matching private key for this peer.
- `AllowedIPs = 10.10.0.10x/32` — exactly the client's address. The VPS accepts packets
  from this peer only with that source address (see §10), and sends traffic for that
  address to this peer. One peer per device, whichever profile is up.
- No `Endpoint` and no `PersistentKeepalive`: the VPS learns each client's address and
  port from its first packet, as with the Pi.

```
sudo systemctl reload wg-quick@wg0
```
Applies the new peers **without taking the tunnel down**. `reload` runs `wg syncconf`,
which updates the peers of the running interface: the Pi's tunnel is not interrupted.

```
sudo wg show
```
Must show three peers: the Pi, the phone and the laptop. The new ones show no handshake
until each client connects for the first time.

**Why `reload` here and `stop`/`start` for the Pi?** `reload` updates peers but does not
add routes. `10.10.0.101` and `10.10.0.102` are inside `10.10.0.0/24`, which is already
routed into `wg0` by the interface `Address`, so no new route is needed. The Pi peer
brought a new network, `<HOME_LAN_SUBNET>`, which needs a route; that is why it was added
with `stop`/`start` ([RASPBERRY-WIREGUARD.md §6](RASPBERRY-WIREGUARD.md#6-add-the-pi-as-a-peer-on-the-vps)).
Rule of thumb:

- New peer inside the VPN range → `reload`.
- New peer that brings a new network → `stop` → edit → `start`.

Editing `wg0.conf` while the tunnel is up is safe in this case because only `[Peer]`
sections are added: the hook lines are unchanged, so the `PostDown` lines still match the
rules in the kernel (see [VPS-WIREGUARD.md §10](VPS-WIREGUARD.md#10-changing-hooks-safely)).

## Part D — Tests

### 8. Test the laptop from outside home
Run the tests from a network outside home, for example through the phone's hotspot
(with the phone's own tunnel off). At home, the local network and the SPLIT route share
`<HOME_LAN_SUBNET>`, and the results are confusing.

#### 8.1 SPLIT
```
sudo wg-quick up casa-split
```
Brings the SPLIT profile up. The output shows the route it adds through `casa-split` for
`<HOME_LAN_SUBNET>`. `10.10.0.0/24` needs no extra line: the `/24` in `Address` already
routes it into `casa-split` (with a `/32` `Address`, as in the first attempt, a second
`ip -4 route add 10.10.0.0/24` line appears).

```
sudo wg show
```
Must show the VPS peer with a recent handshake and growing `transfer` values.

```
ping -c 3 10.10.0.1 ; ping -c 3 10.10.0.2 ; ping -c 3 <HOME_ROUTER_IP>
```
Pings the hub, the Pi and the home router. All three must answer. The TTL of the replies
drops by one at each hop: `64` from the VPS, `63` from the Pi (one hop through the VPS)
and `62` from the router (through the VPS and the Pi), assuming the router starts at `64`
like most Linux-based routers.

```
curl -4 ifconfig.me
```
Prints the public IPv4 the internet sees. With SPLIT it must be the **local network's**
public IP: SPLIT does not route the internet.

```
sudo wg-quick down casa-split
```
Takes the SPLIT profile down and removes its routes.

#### 8.2 FULL
```
sudo wg-quick up casa-full
```
Brings the FULL profile up. The output shows what `wg-quick` does for a full tunnel:
`resolvconf` registering the `DNS` line, `fwmark 51820` on the tunnel, the `ip rule`
policy rules, the default routes in table `51820` for IPv4 and IPv6, and an `nft` table
(`wg-quick-casa-full`) that drops packets for `10.10.0.102` arriving from other interfaces
and keeps the `fwmark` on the replies from the endpoint, so reverse-path filtering does
not drop them.

```
curl -4 ifconfig.me
```
Must print `<VPS_PUBLIC_IP>`: the internet traffic leaves from the VPS. This proves both
the FULL profile and the `MASQUERADE` hook on the VPS.

```
curl -6 --max-time 5 ifconfig.me
```
Must fail (it timed out after 5 seconds here; on a network without IPv6 it fails
immediately): IPv6 is captured by `::/0` and dropped, so it does not
leak through the local network.

```
resolvectl status casa-full 2>/dev/null || cat /etc/resolv.conf
```
Shows the resolver in use: with systemd-resolved, the DNS server of the `casa-full`
interface; otherwise (`||`), the content of `/etc/resolv.conf`. It must show
`nameserver 9.9.9.9` (or `9.9.9.9` as the interface's DNS server).

```
ping -c 3 <HOME_ROUTER_IP>
```
Must still answer: `0.0.0.0/0` includes the home LAN, which the hub routes to the Pi.

```
sudo wg-quick down casa-full
```
Takes the FULL profile down. The policy rules, the routes and the `resolvconf` entry are
removed, and the laptop is back to its normal routing and DNS.

### 9. Test the phone on mobile data
With Wi-Fi off, so the phone is outside the home network:

- **`casa-split`** — the app shows a recent handshake and data received and sent.
  `http://<HOME_ROUTER_IP>` loads the router page in the browser.
- **`casa-full`** — a "what is my IP" website shows `<VPS_PUBLIC_IP>`, and
  [test-ipv6.com](https://test-ipv6.com) reports no IPv6 connectivity.

On the VPS:
```
sudo wg show
```
Must show recent handshakes for the phone (`10.10.0.101/32`) and the laptop
(`10.10.0.102/32`) peers.

## Part E — Diagnostics and rules

### 10. Handshake but no traffic: source address filtering
The handshake checks **only the keys**. After it, WireGuard filters every packet by its
source address: the VPS accepts a packet decrypted with a peer's key only if its source
address is inside that peer's `AllowedIPs`. Anything else is dropped silently, with no log
message by default (only a counter on the receiving side).

So a wrong `Address` in a client profile gives: handshake OK, no data, pages do not load.
This happened while building this setup: the phone's FULL profile first had the laptop's
address. The keys were right, so the handshake succeeded, but every packet carried
`10.10.0.102` as its source while arriving with the phone's key, and the VPS dropped them
all. It was found by comparing the `Address` lines of the phone and laptop profiles.

When a tunnel has a handshake but no traffic, **check `Address` first**. Two checks help
to locate the problem:

- With the profile up, open an IP address directly in the browser (for example
  `https://1.1.1.1`). If it loads, routing works and the problem is DNS; if it does not,
  the problem is in the tunnel or the routing.
- On the VPS:
  ```
  ip -s link show wg0
  ```
  Shows the interface counters. Packets that pass decryption but fail the source check
  are dropped before they reach `wg0`: they never appear in `tcpdump -i wg0`, they do not
  add to the peer's `transfer` in `wg show`, and they increase the `RX errors` counter
  instead. If that counter grows while the client is sending, the source address is
  wrong.

For correctly addressed traffic, `sudo tcpdump -ni wg0 host 10.10.0.101` on the VPS is
still useful for DNS and MTU questions: it shows the client's DNS queries and TCP
connections that stall.

### 11. Rules
- Real keys and addresses live only on the devices, never in this repository.
- Every file that contains a private key has permissions `600`.
- Never bring SPLIT and FULL up at the same time on the same device.
